# GrayDraft 优化与验证工作流（2026-11-02）

> **文档类型：历史记录。** 正文保留当时的上下文与结论。 [当前文档入口](../README.md)

本轮先统一生成完成、答案提交与评测留证。逐要点证据覆盖、来源 ID 分组、入库故障恢复和全局并发治理属于后续工作；不能把本轮实现理解为完整架构升级已经验收。

## 1. 当前问答流程

```text
检索/补读 → 生成候选答案（缓冲）→ 确认模型流完成
         → 现有答案门禁 → 提交 answer.delta → run.completed
```

- Gateway 保留上游 `finish_reason`，Core 区分正常 stop、长度耗尽、过滤、流内错误、无完成标记的 EOF。为兼容仅发送 `[DONE]` 的服务，也接受该传输完成标记，但不能由此推断其语义质量。
- 生成失败即丢弃候选正文；超时、取消、其他失败分别以 expired、cancelled、failed 结束，不再因已有正文而返回成功。
- 门禁在正式正文提交之前执行；拒绝后的安全替代回复直接提交，不交给模型再次改写。只有明确证据缺口可进入原有有限补查，版本/来源等硬约束拒绝不触发无目标补查。
- 非空答案不能绕过空证据、引用不足、版本冲突、既有高风险来源策略。跨语言词面重叠评分仍是诊断信号，**现有门禁不证明全部事实关系正确**。
- Gateway 在已经输出任何增量后不再拼接备用模型。队列不重投已报告终态的模型协议错误和最终成文失败；用户侧新请求仍可显式重试。其他基础设施错误保留原消费策略。
- 普通答案和多篇总览都先缓冲再提交，因此首正文时间包含生成与校验等待；本轮未实现长答案按已校验段落渐进提交。

## 2. 每个问题先确定失败层

| 失败层 | 先检查 | 应采取的动作 |
| --- | --- | --- |
| 语料/入库 | 原文是否存在、ready 后是否可检索 | 独立工作区复现，不修改已冻结赛事语料 |
| 检索/补读 | 召回块是否包含缺失事实，来源是否正确 | 固定问题和语料，检查选段；不要先改成文提示 |
| 成文 | 证据中已有事实，候选答案是否遗漏或串篇 | 使用对应证据与单元夹具验证；加入不应强制包含背景实体的反例 |
| 协议/执行 | finish_reason、错误、截止、是否出现完成事件 | 先跑故障测试，确认没有半截正文提交；不要仅延长超时 |
| 门禁 | 门禁是否检查生成后的候选答案；替代回复是否被重写 | 检查事件顺序和提交次数，门禁异常不得提交正文 |
| 评分 | 拒答中是否仅重复关键词，题目是否被改写 | 离线重评分，与原文关系抽查分别报告 |

每轮只验证一个主要假设。修改评分、修改检索、修改生成应分别记录；不能用重试后的成功覆盖首次失败。

## 4. 执行顺序

以下命令均从仓库根目录执行，括号中的 `cd` 只作用于该命令。

### 4.1 先做离线重评分

```bash
python3 tests/contest/edu/retest_after_upgrade.py \
  --replay tests/contest/edu/runs/20261102T071837583148Z_full.json
```

不调用 API、不重新生成答案，另存新的 replay 文件，并报告分数变化。历史记录缺少清单快照时，必须与所选清单指纹、问题一致，否则拒绝重评。不能用离线重评分代替新代码回归。

### 4.2 运行相关故障与单元测试

```bash
(cd internal/core && go test -race ./service/agent ./service/llmclient ./repository/nats ./repository/postgres)
(cd internal/gateway && go test -race ./handler ./service/llm ./service/provider)
(cd internal/graydraft && go test ./pkg/nexus)
python3 -m unittest discover -s tests/contest/edu -p 'test_retest_after_upgrade.py'
```

必保反例包括：正文后报错、长度耗尽、无终态 EOF、部分输出后兜底、门禁拒绝/异常、缺篇、缺名称、重试改问法、运行中源码变化。

### 4.3 构建并启动开发镜像

```bash
docker compose -f deploy/docker-compose/docker-compose.dev.yml --env-file deploy/config/dev/.env.ports build core gateway
docker compose -f deploy/docker-compose/docker-compose.dev.yml --env-file deploy/config/dev/.env.ports up -d --no-deps core gateway
```

测试开始后不要继续改生产源码或重建运行镜像。

### 4.4 定向复现，然后运行完整回归

```bash
python3 tests/contest/edu/retest_after_upgrade.py --only paper-theme,paper-infra
python3 tests/contest/edu/retest_after_upgrade.py
```

默认跳过缓存、不改问法、不做客户端重试。未知题目 ID 会在访问网络前报错。

若需要衡量有限重试的恢复收益，另开一轮：

```bash
python3 tests/contest/edu/retest_after_upgrade.py --max-retries 2
```

每题最多请求三次，成功即停止；每次保持同一个问题，保留首次和最终判定及全部原始回答。首轮命中率、最终命中率分别报告。

### 4.5 检查结果与退出码

| 退出码 | 含义 |
| --- | --- |
| 0 | 有效回归中所有可答题命中、拒答题明确拒答；或离线重评结果全部通过 |
| 1 | 存在部分、未命中、错误或拒答不合格，原始记录仍保存 |
| 2 | 参数/清单错误、运行中环境变化，或重评来源轮次已标无效 |

成功指标为当前清单的关键词评分，并不自动代表 S1、语义正确性或生产容量验收。

## 5. 后续优化顺序

1. 恢复原始开放规模题和双来源对照题，建立原题集验收清单；补充未参与调优的问法与材料。
2. 引入逐要点需求与证据覆盖，区分检索缺口、成文漏项与关系错误；用稳定来源/章节 ID 替代标题归组，并分离篇目覆盖范围和并发数。
3. 在独立工作区完成新入库、QA 失败不阻塞 ready、重复投递与重启恢复验证。
4. 量测并发、首正文时间、P95、错误率和模型调用成本，再配置全局预算与并发限制。

每项完成后更新实现状态、对应记录和未验证边界。下一步计划见 [升级优化落实与下一步](upgrade-next-steps-2026-11-02.md)。

## 7. 总览尾延迟的后续优化

已为短概述增加独立模型层配置，开发环境启用快层；有必保型号的概述继续用复杂层，普通问答与生产默认模型保持原配置。全部已读证据保留，仅前置型号定义块。快层全量替换、删去背景、空闲触发竞速及自动纠正均未通过收益/质量审查，未保留。另有绝对耗时触发的有界竞速候选：开发测试 4000 ms、每总览最多一个额外请求、每 Core 进程同时最多两个额外请求；生产默认关闭。首批备份没有先完成，不能把整批变快归功于竞速。

每次优化按“保留失败实验 → 检查完整回答与事实关系 → 重复对照 → 完整回归”的顺序验收，不能只取最快或通过的一次。重复测试增加并披露轮间间隔，以区分低负载延迟和突发限流；小样本不报告总体 P95。实现、最终验证记录和回退方式见[尾延迟优化记录](tail-latency-optimization-2026-11-02.md)。
